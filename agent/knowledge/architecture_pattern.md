# Architecture Patterns

Architect 角色的模式参考库。核心原则：**模式服务于需求规模，不为模式而模式**。

## 选型速查

| 项目规模 | 推荐结构 |
| --- | --- |
| 单人工具 / 脚本 | 单文件或简单包结构，够用即可 |
| 小型 Web 应用（MVP） | 单体 + 分层架构，单数据库 |
| 中型应用 | 模块化单体（按领域分模块），必要处引入缓存/队列 |
| 大型 / 多团队 | 才考虑服务拆分；MVP 阶段禁止微服务 |

## 常用模式

### 分层架构（默认首选）

```text
Presentation（路由 / 控制器 / UI）
        ↓
Service（业务逻辑、事务边界）
        ↓
Repository（数据访问，隔离 ORM/SQL）
        ↓
Database
```

规则：依赖只能向下；上层不感知数据库细节；业务逻辑不写在控制器里。

### 模块化单体

按业务领域（而非技术层）划分顶层模块，模块间只通过公开接口交互。
适合中型项目，为未来可能的拆分预留边界。

### 前后端分离

前端 SPA/SSR + 后端 REST/JSON API。契约（api.md）先冻结再并行开发。
简单管理后台可用服务端模板渲染，不强上 SPA。

## API 设计约定

- REST 风格：资源名词复数、HTTP 动词表达操作、状态码语义正确。
- 统一错误结构：`{ "error": { "code": ..., "message": ... } }`。
- 版本策略：路径前缀 `/api/v1/`。
- 列表接口默认分页；禁止无上限返回全表。

## 通用原则

- 单一职责、依赖倒置：核心逻辑不依赖框架细节。
- 配置外置：环境差异全部通过配置注入。
- 无状态服务优先：状态放数据库/缓存，服务可水平扩展。
- 每个重要取舍写入 `memory/decision_log.md`。
