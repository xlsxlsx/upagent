# Design Pattern（设计模式知识）

常用模式的适用场景与滥用警示。原则：先看是否需要，再看用哪个。

## 高频实用模式

| 模式 | 适用场景 | 本项目示例 |
| --- | --- | --- |
| 依赖注入 | 隔离外部能力，可测试 | reason_fn/decide_fn/review_fn 注入 |
| 策略 | 同一动作多种算法可切换 | 关键词检索 vs embedding 检索 |
| 观察者/发布订阅 | 一对多解耦通知 | communication/event.py EventBus |
| 门面 | 收拢子系统入口 | MemoryStore 对三个记忆文件 |
| 工厂方法 | 构建逻辑复杂或依赖环境 | `RepositoryMap.scan()` / `SymbolIndex.from_root()` |
| 模板方法 | 流程固定步骤可变 | Tool.run 约定 + 各工具实现 |

## 使用纪律

- 模式服务于问题，不是目标；能用函数解决不上类，能用类解决不上继承树。
- 两个以上分支才引入策略；一个实现 + 可能的将来 ≠ 引入抽象的理由。
- 单例慎用：全局可变状态让测试与并发变难，优先显式传递。

## 反模式警示

- God Object：一个类了解所有事 → 按职责拆分。
- 贫血模型 + 巨型 Service：数据与行为分离过度 → 行为回归数据所有者。
- 过度抽象：只有一个实现的接口层层包装 → 删掉中间层。
