# Coding Standard

所有工程师角色共同遵守的编码规范。与项目已有代码风格冲突时，**优先与现有代码保持一致**。

## 通用原则

- 代码首先写给人看：清晰 > 聪明。
- 一个函数只做一件事；超过约 50 行考虑拆分。
- 显式优于隐式：不依赖魔法行为、隐藏副作用。
- 同一个概念在整个代码库中只用一个名字。

## 命名

- 变量/函数：动词开头的函数名（`get_user`、`send_email`），名词的变量名。
- 布尔值：`is_` / `has_` / `can_` 前缀。
- 禁止无意义命名（`data1`、`temp`、`aaa`）与拼音混写。
- 遵循目标语言惯例（Python `snake_case`、JS/TS `camelCase`、类 `PascalCase`）。

## 注释

- 解释「为什么」，不复述「是什么」。
- 公共 API、复杂算法、非直观取舍必须有注释/文档字符串。
- 注释与代码同步更新，过期注释比没有更糟。
- 禁止留下大段被注释掉的死代码。

## 错误处理

- 边界处校验输入，尽早失败（fail fast）。
- 禁止空 catch / 裸 `except`：要么处理、要么记录并向上抛。
- 错误信息包含上下文（谁、做什么、为什么失败），但不含敏感数据。

## 函数与模块

- 参数超过 4 个考虑聚合为对象/数据类。
- 依赖方向单一：底层模块不得反向依赖上层。
- 禁止循环依赖；出现即视为设计问题需要重构。

## 测试

- 测试命名描述行为：`test_login_fails_with_wrong_password`。
- 一个测试验证一个行为；断言明确，不写恒真断言。
- 测试之间相互独立，不依赖执行顺序。

## 提交

- 遵循 `tools/git.md` 的提交规范。
- 一次提交 = 一个完整意图；不混合无关改动。
